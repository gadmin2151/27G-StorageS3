# Контекст проекта 27g-StoregeS3

Состояние на **2026-10-12**, версия **0.1.0**. Это переносимая запись требований, принятых решений и проверок для человека или агента, продолжающего разработку после клонирования. История прежнего чата не требуется. Актуальность поведения определяют исходники и новые проверки; этот документ следует обновлять вместе с существенными изменениями.

## Что заказал пользователь

Собственное лёгкое и быстрое S3-совместимое хранилище, похожее по назначению на MinIO, с именем **27g-StoregeS3**. Репозиторий называется **27G-StorageS3**. Основное управление должно выполняться в удобной русской веб-панели со встроенной Wiki. Развёртывание — Docker; установка и объединение серверов в кластер должны быть простыми.

Нужны режим объединения ёмкости по принципу RAID0, зеркалирование RAID1 и RAID10 с чётным числом узлов, начиная с четырёх. Важны синхронизация копий, очереди загрузки, ограниченное использование RAM и кэш частых обращений, безопасность при сетевой эксплуатации. Полностью отказоустойчивый кластер остаётся целевой возможностью, а не свойством текущего координатора. Пользователь также попросил публиковать исходники, README с настоящими скриншотами и этот контекст для работы с разных устройств.

## Текущая архитектура и файлы

Один процесс-координатор обслуживает S3, административный API и статическую веб-панель. Каталог объектов и аутентификация хранятся в двух SQLite БД, blobs — на локальном узле и/или HTTP-узлах. Используются Node.js 22.13+, встроенный `node:sqlite` и стандартные модули; внешних npm-зависимостей, Redis и отдельного сервера БД нет. Панель работает без фронтенд-сборки.

| Файл | Назначение |
| --- | --- |
| `src/server.mjs` | HTTP-маршрутизация, защита панели, административный API, блокировка второго координатора, автоматическая проверка реплик |
| `src/storage.mjs` | SQLite-каталог, размещение, потоковые загрузки, очередь, LRU-кэш, миграция, проверка/восстановление и сборка мусора |
| `src/auth.mjs` | Первоначальная настройка, scrypt-пароли, сессии/CSRF, S3-ключи и их шифрование, журнал административных событий |
| `src/s3.mjs` | SigV4, presigned URL, поддерживаемые S3-операции, XML, диапазоны, checksum и явные ошибки для неподдерживаемых запросов |
| `src/node.mjs` | Отдельный узел: авторизованные health/blob-запросы, запись на диск и ограничение загрузок |
| `web/index.html`, `web/app.js`, `web/style.css` | Русская панель: обзор, бакеты/объекты, кластер, ключи, настройки и встроенная Wiki с поиском |
| `tests/app.test.mjs`, `tests/s3.test.mjs`, `tests/storage.test.mjs` | Функциональные тесты приложения, S3 и хранения, включая реальные HTTP-узлы на loopback |
| `Dockerfile`, `compose.yaml` | Координатор и профиль `cluster` с четырьмя узлами; отдельный volume для каждого |
| `compose.node.yaml`, `scripts/init-cluster.sh` | Запуск узла на другом сервере и создание его секрета |
| `compose.https.yaml`, `Caddyfile`, `.env.example` | Необязательный HTTPS через Caddy и пример настроек |
| `README.md`, `docs/S3-COMPATIBILITY.md` | Установка, эксплуатация, ограничения, точная совместимость и примеры клиентов |

Панель открывается по `http://localhost:9000/console/`; S3 endpoint — `http://localhost:9000`, стандартный регион — `us-east-1`. Начальная настройка требует случайный setup token и создаёт администратора без пароля по умолчанию. Docker публикует обычный порт координатора на loopback. Настройка Docker, дисков, DNS и сети выполняется на сервере; дальнейшее управление хранилищем доступно из панели.

## Важные решения и инварианты

- **Объектное размещение.** RAID0 хранит одну копию целого объекта; RAID1 — на всех выбранных узлах, минимум двух; RAID10 — в одной из зеркальных пар, минимум четыре узла и чётное количество. Пары определяются порядком узлов. Rendezvous hashing выбирает узел/пару и пока не учитывает размер объекта и ёмкость диска. Это не чередование блоков одного файла.
- **Подтверждение записи.** Сначала временный файл и checksum, затем все обязательные реплики с `fsync`, затем фиксация SQLite. Ошибка перезаписи сохраняет ранее подтверждённый объект. В RAID1 новая запись требует всех выбранных узлов; в RAID10 — обоих узлов целевой пары. Автоматической записи в деградированное зеркало нет.
- **Чтение и целостность.** Некэшированная реплика проверяется целиком по SHA-256; повреждение одной копии позволяет пробовать другую. Удалённая реплика перед выдачей загружается во временный файл координатора. Даже небольшой Range может потребовать чтения всего объекта. Кэш не служит долговечным хранилищем.
- **Миграция.** Новый состав сначала проверяется, нужные копии создаются и проверяются, затем каталог и топология меняются транзакцией. До успеха действует старая топология. Фиксация записей ждёт общего mutex, чтения продолжаются. Нужна дополнительная ёмкость; возобновления миграции после перезапуска нет.
- **Ограничение ресурсов.** Значения координатора по умолчанию: 4 активные загрузки, 32 ожидающие, 64 MiB RAM-кэша; кэшируются объекты до 1 MiB, максимум 4096 записей. Тела загрузок идут во временные файлы. Переполнение очереди даёт `503 SlowDown`. Веб-панель меняет кэш, параллелизм и интервал проверки; размер объекта и лимит очереди задаются при запуске.
- **Восстановление.** Проверка реплик вручную и автоматически каждые 15 минут; интервал `0` отключает автоматический запуск. Исправная копия используется для восстановления. При проверке собираются старые/неудачные blobs после часового защитного периода; удаление объекта освобождает место не сразу.
- **Один координатор.** Локальный lock/lease предотвращает параллельные старты на одном каталоге. Это не distributed fencing или consensus. Нельзя запускать несколько координаторов над общим volume либо несколько узлов над одним каталогом blobs. Работа с сетевыми файловыми системами не подтверждена.

## Фактическая совместимость S3

Поддерживаются path-style и AWS Signature V4; ключи `readonly`/`readwrite`, необязательное ограничение бакетами; `ListBuckets`, `CreateBucket`, `HeadBucket`, `DeleteBucket`, `GetBucketLocation`, `ListObjects`/`ListObjectsV2`, `PutObject`, `GetObject`, `HeadObject`, `DeleteObject`, presigned GET/PUT. Есть prefix/delimiter/пагинация, одиночный Range и `If-Match`/`If-None-Match` при чтении. Сохраняются `Content-Type`, ETag/MD5, SHA-256, время изменения; проверяются поддерживаемые checksum-заголовки. Объект — до 5 GiB одним PUT, но таймауты и скорость сети могут снизить практический предел.

**Нет:** multipart/resume, AWS streaming signatures и trailers, virtual-hosted-style, CopyObject, пакетного удаления, versioning, пользовательских `x-amz-meta-*`, полноценного IAM/bucket policies/ACL, STS, lifecycle, CORS, S3-шифрования, object lock. Точный контракт и инструкции клиентам — в `docs/S3-COMPATIBILITY.md`. Использовать низкоуровневый одиночный PUT: высокоуровневые клиенты могут незаметно включить multipart. Не объявлять полную совместимость с AWS S3/MinIO.

## Безопасность и данные

Реализованы scrypt, случайные ограниченные по времени сессии, HttpOnly/SameSite cookies, CSRF/Origin, ограничение входов, проверки SigV4/времени/checksum, CSP и экранирование интерфейса. Объекты отдаются как attachment, чтобы пользовательский HTML/SVG не исполнялся в origin панели. S3-секреты зашифрованы AES-256-GCM ключом `master.key` в том же защищённом каталоге; полный захват volume раскрывает их. Blobs приложением на диске не шифруются. Сессии живут в памяти и теряются после перезапуска.

Межузловой протокол использует bearer token и доверяет координатору; HTTP допустим в доверенной изолированной сети/VPN, иначе нужен TLS. Порты узлов не предназначены для Интернета. Для публичного S3 нужен HTTPS; доступ к панели рекомендуется ограничить VPN/allowlist. Доверять IP-заголовку можно только от явно настроенных proxy. Контейнеры приложения работают без root, с read-only rootfs и сброшенными capabilities.

Нет независимого аудита, MFA/OIDC, полного неизменяемого audit всех S3-запросов, квот и KMS. Текущие меры не означают доказанную защищённость от любых интернет-атак.

Git переносит код и контекст разработки, **не рабочие данные**. Не публиковать `.env`, `secrets/`, каталоги данных, SQLite/WAL/SHM, `master.key`, setup/node/S3-токены, cookies, пользовательские объекты или приватные журналы. Скриншоты должны содержать только демонстрационные данные. Для переноса действующего хранилища нужен отдельный согласованный backup всех volumes и секретов; одного каталога blobs недостаточно. Не использовать `docker compose down -v` для обычного перезапуска — он уничтожает volumes.

## Проверки и продолжение на другом устройстве

После клонирования читать `AGENTS.md`, этот файл и README. Для разработки нужен Linux с Node.js 22.13+; `npm install` сейчас не требуется:

```sh
node --version
node --test tests/*.test.mjs
node src/server.mjs
```

Для Docker:

```sh
docker compose config --quiet
docker compose up -d --build
```

На этапе создания версии 0.1.0 зафиксирован результат **28/28 проходящих функциональных тестов**. Проверены жизненный цикл S3, подписи/права/checksum, безопасные пути, setup/CSRF, блокировка второго координатора, очередь/кэш, RAID10, отказ и восстановление реплики, перезапуск, миграция/откат. Через браузер проверялись вход, создание бакета, загрузка файла и запуск проверки реплик.

Docker-конфигурация была проверена, однако запуск контейнеров на исходной среде разработки был заблокирован доступом к Docker Engine. Это ограничение той среды, а не результат тестирования Docker в других окружениях. Функциональные тесты не заменяют нагрузочные испытания, тесты потери питания/разделения сети, реальную матрицу SDK или независимый аудит. Результат нового запуска фиксировать отдельно с датой и командой.

## Следующие приоритеты

1. Спроектировать реплицированный каталог с quorum/consensus, fencing, безопасным обновлением и failover координатора; определить поведение при потере связи и проверить сценарии отказов. Зеркала blobs сами по себе не решают отказ метаданных.
2. Реализовать multipart и совместимость с реальными SDK/CLI, включая streaming/checksum trailers; добавить соответствующие интеграционные сценарии и явно обновлять контракт.
3. Измерить производительность, память и I/O. Устранить узкое место общего mutex и полное предварительное чтение крупных объектов, сохранив инварианты подтверждения и целостности; добавить настраиваемые таймауты и возобновляемые фоновые работы.
4. Упростить присоединение серверов и эксплуатацию из панели: состояние длительных задач, безопасные операции обслуживания, понятное восстановление и дальнейшее развитие Wiki.
5. Провести независимую проверку безопасности, испытания перегрузки и восстановления; добавить мониторинг, более полный аудит, управление доступом и проверяемые резервные копии.

Порядок — отправная точка, а не обещание готовых функций. При продолжении учитывать новые пожелания пользователя и сохранять проверяемое описание состояния.
