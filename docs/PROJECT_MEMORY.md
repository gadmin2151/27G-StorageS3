## Что заказал пользователь

Собственное лёгкое и быстрое S3-совместимое хранилище, похожее по назначению на MinIO, с именем **27g-StoregeS3**. Репозиторий называется **27G-StorageS3**. Основное управление должно выполняться в удобной русской веб-панели со встроенной Wiki. Развёртывание — Docker; установка и объединение серверов в кластер должны быть простыми.

Нужны режим объединения ёмкости по принципу RAID0, зеркалирование RAID1 и RAID10 с чётным числом узлов, начиная с четырёх. Важны синхронизация копий, очереди загрузки, ограниченное использование RAM и кэш частых обращений, безопасность при сетевой эксплуатации. Пользователь также попросил публиковать исходники, README с настоящими скриншотами и этот контекст для работы с разных устройств.

Для версии 0.2 пользователь выбрал multipart/resume, версии и корзину, роли/MFA/квоты, мониторинг, мастер обслуживания и подключение дисков/SMB/CIFS. Уточнил: **ровно пять версий содержимого вместе с текущей**, управляющие серверы **master и slave** с назначаемыми ролями. Дополнительно нужен публичный домен в настройках, который используется в новых ссылках; CORS настраивается отдельно.

## Текущая архитектура и файлы

Активный координатор обслуживает S3, административный API и статическую веб-панель. В обычном режиме три SQLite БД содержат каталог, аутентификацию и временные ссылки; blobs находятся на локальном узле и/или HTTP-узлах. В отдельном HA-режиме два координатора используют собственные SQLite-проекции, а авторитетный зашифрованный снимок метаданных и lease хранятся в кворуме из трёх etcd voters. Используются Node.js 22.13+, встроенный `node:sqlite` и стандартные модули; внешних npm-зависимостей нет. Панель работает без фронтенд-сборки.

Для входа с начальным паролем через сеть требуется случайный setup token; прямой локальный запуск только на loopback без PUBLIC_ORIGIN и доверенных прокси допускает вход без токена. Смена пароля отключает требование токена, а перезапуск не сбрасывает учётные данные. Существующие пользователи сохраняются. Docker публикует обычный порт координатора на loopback. Настройка Docker, дисков, DNS и сети выполняется на сервере; дальнейшее управление хранилищем доступно из панели.

## Важные решения и инварианты

- **Объектное размещение.** RAID0 хранит одну копию целого объекта; RAID1 — на всех выбранных узлах, минимум двух; RAID10 — в одной из зеркальных пар, минимум четыре узла и чётное количество. Пары определяются порядком узлов. Rendezvous hashing выбирает узел/пару и пока не учитывает размер объекта и ёмкость диска. Это не чередование блоков одного файла.
- **Подтверждение записи.** Сначала временный файл и checksum, затем все обязательные реплики с `fsync`, затем фиксация SQLite. Ошибка перезаписи сохраняет ранее подтверждённый объект. В RAID1 новая запись требует всех выбранных узлов; в RAID10 — обоих узлов целевой пары. Автоматической записи в деградированное зеркало нет.
- **Чтение и целостность.** Некэшированная реплика проверяется целиком по SHA-256; повреждение одной копии позволяет пробовать другую. Удалённая реплика перед выдачей загружается во временный файл координатора. Даже небольшой Range может потребовать чтения всего объекта. Кэш не служит долговечным хранилищем.
- **Миграция.** Новый состав сначала проверяется, нужные копии создаются и проверяются, затем каталог и топология меняются транзакцией. До успеха действует старая топология. Фиксация записей ждёт общего mutex, чтения продолжаются. Нужна дополнительная ёмкость; возобновления миграции после перезапуска нет.
- **Ограничение ресурсов.** Значения координатора по умолчанию: 4 активные загрузки, 32 ожидающие, 64 MiB RAM-кэша; кэшируются объекты до 1 MiB, максимум 4096 записей. Тела загрузок идут во временные файлы. Переполнение очереди даёт `503 SlowDown`. Веб-панель меняет кэш, параллелизм и интервал проверки; размер объекта и лимит очереди задаются при запуске.
- **Восстановление.** Проверка реплик вручную и автоматически каждые 15 минут; интервал `0` отключает автоматический запуск. Исправная копия используется для восстановления. В обычном режиме старые/неудачные blobs собираются после часового защитного периода. Версии и части незавершённых multipart не являются мусором. В HA физическая сборка мусора отключена, старые blobs продолжают занимать место.
- **Изоляция процессов.** Локальный lock/lease предотвращает параллельные старты на одном каталоге. Нельзя запускать несколько координаторов над общим volume либо несколько узлов над одним каталогом blobs. HA использует отдельный volume каждого координатора и fencing через etcd, а не общий SQLite на NFS/SMB.
- **Версии.** Пять версий содержимого включают текущую; delete markers не входят в этот лимит. Удаление создаёт корзину, полная очистка удаляет сохранённые версии. При каждой смене текущего объекта выдаётся новая access-generation: восстановление или удаление последней версии не оживляет прежнюю временную ссылку.
- **Квоты и multipart.** Сохранённые версии, части и активные резервы учитываются до фиксации, с защитой от параллельного превышения. Подтверждённые части уже находятся на всех обязательных репликах. Завершение собирает объект и фиксирует новую версию. Все эти данные участвуют в миграции и проверке реплик.

## Фактическая совместимость S3

Поддерживаются path-style и AWS Signature V4; ключи с владельцем, ограничениями бакетов/префиксов/действий и сроком; базовые операции бакетов/объектов, presigned GET/PUT, multipart initiate/part/list/complete/abort, GetBucketVersioning/ListObjectVersions и versionId при чтении/удалении. Есть prefix/delimiter/пагинация, одиночный Range и `If-Match`/`If-None-Match` при чтении. Сохраняются `Content-Type`, ETag, SHA-256, время изменения; проверяются поддерживаемые checksum-заголовки. Объект — до 5 GiB целиком или multipart; межузловые таймауты и скорость сети могут снизить практический предел.

**Нет:** AWS streaming signatures и trailers, virtual-hosted-style, CopyObject/UploadPartCopy, пакетного удаления, отключения/приостановки versioning, пользовательских `x-amz-meta-*`, полного IAM/bucket policies/ACL, STS, lifecycle, S3 bucket CORS API, S3-шифрования, object lock. Глобальный CORS есть в настройках приложения. Точный контракт и инструкции клиентам — в `docs/S3-COMPATIBILITY.md`. Реальную матрицу SDK ещё нужно испытать; не объявлять полную совместимость с AWS S3/MinIO.

## Безопасность и данные

Реализованы scrypt, случайные ограниченные по времени сессии, HttpOnly/SameSite cookies, CSRF/Origin, ограничение входов, проверки SigV4/времени/checksum, CSP и экранирование интерфейса. S3 и административное скачивание отдают объекты как attachment, чтобы пользовательский HTML/SVG не исполнялся в origin панели. Временные ссылки панели открывают inline только разрешённые растровые типы с nosniff и CSP sandbox; прочие типы скачиваются. S3-секреты зашифрованы AES-256-GCM ключом `master.key` в том же защищённом каталоге; полный захват volume раскрывает их. Blobs приложением на диске не шифруются. Сессии живут в памяти и теряются после перезапуска.

Межузловой протокол использует bearer token и доверяет координатору; HTTP допустим в доверенной изолированной сети/VPN, иначе нужен TLS. Порты узлов не предназначены для Интернета. Для публичного S3 нужен HTTPS; доступ к панели рекомендуется ограничить VPN/allowlist. Доверять IP-заголовку можно только от явно настроенных proxy. Контейнеры приложения работают без root, с read-only rootfs и сброшенными capabilities.

Добавлены роли admin/operator/viewer, TOTP MFA с recovery codes, квоты пользователей/бакетов и ограничения ключей. Нет независимого аудита, OIDC, полного неизменяемого audit всех S3-запросов и KMS. Текущие меры не означают доказанную защищённость от любых интернет-атак. Привилегированный disk-agent развёртывается отдельно и не должен быть доступен из Интернета.

Git переносит код и контекст разработки, **не рабочие данные**. Не публиковать `.env`, `secrets/`, каталоги данных, SQLite/WAL/SHM, `master.key`, setup/node/S3-токены, cookies, пользовательские объекты или приватные журналы. Скриншоты должны содержать только демонстрационные данные. Для переноса действующего хранилища нужен отдельный согласованный backup всех volumes и секретов; одного каталога blobs недостаточно. Не использовать `docker compose down -v` для обычного перезапуска — он уничтожает volumes.

## Начальная учётная запись — 2026-10-12

По запросу владельца новая установка создаёт стандартного администратора; публичная начальная пара указана в README и на форме входа. Она создаётся только при пустой таблице пользователей, с отдельным признаком `defaultCredentials` и scrypt-хешем. Обновления и перезапуски не заменяют существующего администратора. Обычная смена пароля сохраняет минимум 12 символов, снимает признак начального пароля и отзывает прежние сессии. Приватные токены, хеши, данные экземпляров и журналы в Git не добавлены.

Пока пароль начальный, сетевой вход требует `setup.token`. Исключение действует только при фактической привязке HTTP-сервера к loopback, loopback-адресе TCP-клиента, пустом `PUBLIC_ORIGIN` и отсутствии доверенных proxy. Docker/wildcard-привязка требует токен даже при открытии панели через localhost; Host и forwarded-заголовки не предоставляют исключение. ## Версия 0.2 — 2026-10-12

Реализованы выбранные владельцем возможности с управлением через прежнюю циановую панель:

- **Multipart:** S3 и административный API, сохранение частей на обязательных репликах до ACK, продолжение после перезапуска. Панель использует части по 8 MiB, хранит идентификатор очереди отдельно для каждого пользователя, после повторного выбора файла проверяет его признаки и SHA-256 сохранённых частей. Пауза во время вычисления SHA-256 не создаёт второй uploadId/параллельный поток. Общий лимит объекта остаётся 5 GiB; abandoned uploads надо отменять вручную.
- **История и корзина:** текущая плюс четыре предыдущие версии содержимого, delete markers отдельно; просмотр, скачивание, восстановление и подтверждаемая полная очистка. Прежние текущие объекты мигрируют в первую версию без переноса blobs. В `objects` добавлен `generation`: существующие ссылки сохраняют прежний идентификатор при обновлении, но любая смена текущей версии получает новый UUID. Удаление текущей версии или маркера не оживляет старые ссылки. `shares.blob_id` теперь хранит непрозрачное поколение доступа. Истёкшие ссылки удаляются при запуске/создании; GET списка только фильтрует их, чтобы не менять HA-состояние при чтении.
- **Доступ:** admin/operator/viewer, включение/отключение пользователя, защита последнего активного администратора, квоты байтов и числа сохраняемых объектов/версий. Operator управляет файлами, viewer читает; эти роли не являются изоляцией арендаторов. S3-ключи имеют владельца, допустимые операции, бакеты, префиксы и срок. Отключение владельца/изменение его роли влияет на ключи и сессии. TOTP использует зашифрованный секрет, защищён от повторного timestep и перебора, recovery codes хранятся хешами и применяются один раз. Сессии остаются в RAM, при перезапуске/failover нужен повторный вход.
- **Диагностика:** запросы/ошибки, p50/p95/p99, RAM, очередь, кэш, график и предупреждения о заполнении, offline/shared filesystem, задержках и последней проверке копий. Пороги сохраняются, история и отметки прочтения находятся в RAM. `/api/metrics` требует admin-сессию. Внешней отправки email/webhook пока нет.
- **Обслуживание:** форма изменения топологии сначала показывает оценку ёмкости и переноса с подтверждением. Миграция включает все сохранённые версии и части; возобновления самой миграции после перезапуска ещё нет.
- **Диски:** отдельный disk-agent, реестр серверов из панели, подключение каталогов, существующих ext4/XFS/Btrfs устройств `/dev/...`, SMB3/CIFS и NFSv4. Главный контейнер не получает mount-привилегии. Устройства не форматируются, чужие файлы не импортируются. Агент проверяет занятость устройства на хосте перед каждым mount/retry, держит дескрипторы каталога до завершения I/O, блокирует запись при потере mount, отказывает на symlink и неизвестное состояние. Подробные привилегии и порядок запуска — `docs/DISKS.md`.
- **Адрес сервиса:** настройки `publicOrigin` и отдельные точные CORS origins сохраняются в auth preferences и HA snapshot. Новые временные ссылки, S3 endpoint, multipart Location и примеры Wiki используют публичный адрес. Смена домена требует подтверждения готовности DNS/HTTPS и перехода на новый origin для административных действий. Это не настройка DNS и не выпуск сертификата. Уже выданные URL у получателей не меняются. `PUBLIC_ORIGIN_OVERRIDE` позволяет исправить ошибочный адрес при запуске. CORS действует только на S3, не отменяет SigV4/CSRF/Origin; поддержаны retry-заголовки браузерного AWS SDK.

### Master/slave и пределы HA

Пользователь выбрал два полноценных координатора. Для безопасного автоматического переключения добавлен независимый третий арбитр: по etcd voter на master, slave и witness. На одном Docker-хосте Compose демонстрирует схему, но не защищает от потери этого хоста. Роль master/slave означает предпочтение; право записи выдаёт lease, а commit проверяет владельца lease и revision метаданных в etcd-транзакции. Роль узла назначается в панели и хранится локально. Caddy направляет общий вход на `/ha/ready`; в эксплуатации доступность самого ingress нужно обеспечить отдельно.

SQLite каждого координатора — локальная проекция; авторитетные метаданные сохраняются зашифрованным сжатым снимком в etcd. Подготовленный ответ мутации и Set-Cookie не уходят клиенту до commit. Неудача восстанавливает подтверждённое состояние, включая эффективный кэш/параллелизм при отсутствии runtime-настроек в старом снимке. При таймауте 503 исход commit может быть неопределённым: после восстановления кворума нужно проверить результат. Для HA нужны зеркальные HTTP-узлы, локальное размещение данных/RAID0 недопустимы.

Ограничения первой реализации: полный снимок до 64 MiB несжатого JSON и по умолчанию до 8 MiB сжатого encrypted payload; запросы, включая длинные чтения, сериализованы; физическая GC отключена до fencing удаления на узлах, поэтому старые blobs занимают место. Отказ процесса master проверен с продолжением записи через slave. При потере целого хоста с одной storage-репликой чтение сохраняется, запись требует восстановления зеркала. TLS etcd поддерживает CA/client certificate env files; в Docker демо используется закрытая сеть. Подробности и восстановление — `docs/HA.md`.
