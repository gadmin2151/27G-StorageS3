# Функции и приоритеты развития 27G-StorageS3

Исследование от **12 октября 2026 года**. Состояние нашего проекта сверено с версией 0.1.0, коммитом `bdc959b7100e932d1f07028affae30b3edb8eac9`, исходным кодом и [матрицей S3](S3-COMPATIBILITY.md). Возможности других продуктов проверены по официальной документации; сами продукты в рамках исследования не разворачивались, сравнительных замеров скорости нет.

**Главный вывод:** ближайшее развитие стоит сосредоточить на продолжении загрузок, восстановлении данных, совместимости с обычными S3-клиентами и отказоустойчивом каталоге. Управление каждым механизмом должно появляться в веб-панели вместе с понятными состояниями, ошибками и инструкциями. Увеличение RAM-кэша само по себе эти задачи не решает.

Ниже — исторические предложения для обсуждения и планирования на момент версии 0.1. Это не утверждённые сроки выпуска. После исследования часть функций реализована в **0.2**: актуальное состояние, проверки и ограничения находятся в [руководстве по эксплуатации](OPERATIONS.md#файлы-пользователи-и-мониторинг) и [памяти проекта](PROJECT_MEMORY.md).

Облачные сервисы показывают удобство работы и ожидаемые API. Самостоятельно разворачиваемые системы помогают оценить обслуживание дисков, размещение копий и поведение кластера. Поддержка функции в собственной панели провайдера не обязательно означает поддержку одноимённого S3 API.

| Продукт | Что подтверждено документацией | Что взять за ориентир |

| **Amazon S3** | Загрузка частями с повторной отправкой неудачных частей; версии и маркеры удаления; условные записи | Возобновление больших загрузок, история файла, защита от случайной перезаписи. | **Cloudflare R2** | Multipart, CORS и lifecycle входят в поддерживаемый S3 API. Наличие Object Lock требует строгих правил удаления. [Object Lock](https://docs.wasabi.com/docs/en/object-locking), [dashboard](https://docs.wasabi.com/docs/dashboard), [ссылки](https://docs.wasabi.com/docs/shareio-with-wasabi) |

Для нашего продукта стоит также вывести управление версиями и правами в панель. [Совместимость](https://docs.digitalocean.com/products/spaces/reference/s3-compatibility/) |

## 4. Приоритеты функций

**P0** — основа для важных данных и заявляемого сценария; **P1** — следующий продуктовый этап; **P2** — после подтверждения потребности. Сложность относительная: она учитывает изменения формата хранения, протокола и восстановления, а не только объём интерфейса. P0 не означает, что всё следует выпускать одним большим обновлением.

| Приоритет | Функция | Польза | Сложность / зависимость |
| --- | --- | --- | --- |
| P0 | Multipart и возобновление | Большой файл не загружается заново после обрыва | Высокая: постоянное состояние частей и завершения |
| P0 | Backup/restore с проверкой | Восстановление после потери сервера или каталога | Высокая: согласованность всех данных и секретов |
| P0 для отказоустойчивого кластера | HA каталога и координатора | Сервис переживает отказ управляющего узла | Очень высокая: consensus, fencing, миграция формата |
| P0 | Совместимость с реальными S3-клиентами | Подключение приложений без нестандартных обходов | Высокая: multipart, checksum, операции и CI |
| P0 | Метрики, предупреждения, состояние копий | Проблема видна до потери доступности или места | Средняя; начинать до усложнения кластера |
| P0 перед совместной работой | Пользователи, роли, права ключей, MFA | Приложению или сотруднику не нужен полный доступ | Высокая: единая проверка прав во всех маршрутах |
| P1 | Версии, восстановление и lifecycle | Защита от ошибочной перезаписи и управляемый расход диска | Высокая; формат версий спроектировать вместе с HA |
| P1 | Присоединение, замена, вывод узлов | Обслуживание кластера из панели | Высокая: безопасная миграция и восстановление задач |
| P1 | Внешняя резервная копия / репликация | Отдельная копия за пределами основного сервера | Высокая: журнал изменений и политика удалений |
| P1 | Квоты бакетов/пользователей | Одно приложение не занимает всё место | Средняя: резервирование места под загрузки и версии |
| P1; раньше для backup-сценария | Object Lock | Неизменяемые резервные копии на заданный срок | Высокая; после версий и проверки всех путей удаления |
| P1 | Шифрование объектов на диске | Защита при доступе к накопителю без ключей | Высокая: управление ключами и восстановление |
| P1 | Файловый менеджер и события | Массовые действия, превью, автоматизация приложений | Средняя/высокая: безопасная выдача, постоянные очереди |
| P2 | EC, классы хранения, дедупликация | Экономия ёмкости в подходящих нагрузках | Очень высокая; нужны замеры и проверенные процедуры ремонта |

### 4.1. Загрузки и совместимость

Реализовать `CreateMultipartUpload`, `UploadPart`, `ListParts`, `CompleteMultipartUpload`, `AbortMultipartUpload`, `ListMultipartUploads`. Позже добавить `UploadPartCopy` для больших серверных копирований. Состояние загрузки должно переживать перезапуск; завершение должно атомарно публиковать объект после проверки частей и обязательных копий.

В панели нужен раздел **«Загрузки»**: прогресс, скорость, очередь, пауза, повтор, отмена, история ошибки и срок очистки незавершённых частей. Продолжение после перезагрузки страницы может требовать повторного выбора того же локального файла; это нужно объяснять пользователю. В AWS части можно отправлять независимо и повторять отдельно, а незавершённые загрузки требуют завершения или отмены. [Модель multipart](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html).

Следом добавить `CopyObject`, `DeleteObjects`, `x-amz-meta-*`, теги, сохраняемые HTTP-метаданные, CORS и условные записи. CORS настраивать отдельно для бакетов, сохраняя защиту административного API. Для `If-Match`/`If-None-Match` при записи проверять условие в той же атомарной операции, которая фиксирует объект. [Семантика AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

Совместимость проверять реальными AWS CLI, boto3, JavaScript SDK, `mc` и `rclone` в CI с зафиксированными версиями. Отдельно проверить выбранные backup-клиенты. Важны загрузки выше порога multipart, подписи, checksum/trailers, Unicode-ключи, перезаписи и сбои. Надпись «S3-совместимо» не должна подменять список проверенных операций.

### 4.2. Восстановление, версии и защита от удаления

Нужны три отдельных механизма:

1. **Зеркало** сохраняет доступную копию при отказе носителя, если остальные части системы работоспособны.
2. **Версии** позволяют вернуть файл после ошибочной перезаписи или удаления. В панели — вкладка «История», размер каждой версии, восстановление и корзина на основе маркеров удаления. Старые версии занимают место; нужны сроки хранения и понятный расчёт расхода. [Версии в S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html).
3. **Резервная копия** позволяет восстановить систему после потери всей установки. Нужны расписание, отдельное место хранения, проверка целостности и пробное восстановление.

Backup должен включать согласованный каталог, blobs, настройки, пользователей, ключи и состояние временных ссылок. Секреты в экспортируемом архиве должны быть защищены; ключ расшифрования нельзя хранить только внутри этого же архива. Мастер восстановления должен показывать дату снимка, ожидаемые объекты, найденные копии и результат проверки. Текущую ручную процедуру остановки и копирования всех volumes сохранять до появления проверенного механизма снимков.

Внешнюю копию в другой S3-сервис оформить как задачу с расписанием, ограничением скорости, задержкой синхронизации и повтором ошибок. Отдельно выбирать перенос версий и удалений: автоматическое копирование удаления может уничтожить и резервную копию. Для начала достаточно одностороннего режима; двусторонняя синхронизация потребует разрешения конфликтов.

**Object Lock** добавить после версий: retention, legal hold, различие governance/compliance и проверка запрета удаления через API, панель, lifecycle и сборщик мусора. Блокировка на уровне приложения сама по себе не доказывает защиту от администратора хоста или соответствие нормативам. [Модель Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html).

Lifecycle должен отдельно управлять текущими объектами, старыми версиями и незавершёнными загрузками. Перед сохранением правила панель показывает затронутые данные и ограничения retention. **Истечение временной ссылки не удаляет файл** — это другой срок.

### 4.3. Настоящая отказоустойчивость и простое обслуживание

Архитектуру HA нужно проектировать сейчас, до накопления новых независимых SQLite-таблиц. Для рассматриваемой схемы с одним активным координатором потребуются репликация метаданных, выбор лидера, quorum, защита от двух одновременно пишущих координаторов, стабильный адрес клиента и безопасные обновления схемы. Это направление проектирования, а не единственный возможный вариант HA. Реплицировать нужно также права, ссылки и состояние фоновых задач. Копирование файла SQLite между узлами эту задачу не решает.

Для начального проекта HA разумно рассмотреть **три голосующих узла метаданных**; окончательный состав зависит от выбранного протокола. Чётное число узлов RAID10 относится к хранению объектов, а не к числу голосов в consensus. Два зеркальных диска не становятся автоматически кластером с безопасным переключением управляющего узла.

В панели **«Кластер»** нужны:

- Мастер присоединения: одноразовый ограниченный по времени токен, проверка идентичности узла, защищённое соединение между серверами, выбор диска и хоста/зоны отказа.
- Предварительный план: полезная ёмкость после изменения, объём переносимых данных, временный запас места и риск потери независимых копий.
- Операции «Обслуживание», «Заменить диск», «Вывести узел»: постоянная задача с прогрессом, паузой и ограничением скорости, продолжающаяся после перезапуска.
- Плановая проверка целостности, список повреждений, ремонт из здоровой копии и видимый результат последней проверки.

Garage показывает пользу предварительного расчёта layout: дополнительное место в одной зоне не всегда увеличивает полезную ёмкость при ограничениях размещения копий. Ceph явно учитывает домены отказа. Для нас две копии в контейнерах на одном физическом диске должны показываться как зависимые. [Garage layout](https://garagehq.deuxfleurs.fr/documentation/operations/layout/), [Ceph CRUSH](https://docs.ceph.com/en/tentacle/rados/operations/crush-map/).

### 4.4. Доступ, наблюдение и эксплуатация

**Пользователи и ключи.** Роли «наблюдатель», «оператор», «администратор»; отдельные права приложения на чтение, загрузку и удаление, ограничения бакетом/префиксом, срок действия и ротация. Добавить MFA с восстановлением доступа и журнал значимых действий. Сначала нужна понятная собственная модель прав; совместимость со всем AWS IAM/STS можно расширять позже по требованиям интеграций.

**Панель состояния.** Показывать отдельно доступность координатора, объектов и требуемого числа независимых копий. Добавить задержки p50/p95/p99, ошибки, скорость операций, использование дисков, очередь, попадания в кэш, возраст последнего backup и задержку внешней копии. Предупреждения — в панели и через настраиваемый канал; метрики — в формате Prometheus. Сообщение «все узлы онлайн» не заменяет проверку сохранности.

**Квоты.** Лимиты по объёму и числу объектов для бакета/владельца, предупреждение заранее. Учитывать версии, multipart и зарезервированное место активных загрузок; отдельно показывать логический объём и физические копии. Нельзя складывать показатели одного диска несколько раз только потому, что на нём несколько контейнеров.

**Шифрование и обновления.** Сейчас шифруются S3-секреты, а не содержимое объектов. Для шифрования blobs нужна модель хранения, ротации и восстановления ключей; потеря ключа может сделать копии бесполезными. В панели также нужны диагностика с удалением секретов, срок сертификата и управляемое обновление с backup перед миграцией. Возможность отката определяется совместимостью формата данных, а не только старым Docker-образом. Не давать веб-приложению неограниченный доступ к Docker socket ради кнопки обновления.

### 4.5. Удобство панели и интеграции

| Экран | Предлагаемые возможности |
| --- | --- |
| Бакеты и объекты | Массовый выбор, копирование/перемещение, поиск с пагинацией, фильтры, теги, свойства и версии. Перемещение через copy+delete показывать как составную операцию |
| Просмотр файла | Безопасные миниатюры изображений, просмотр поддерживаемых форматов, Range для видео и больших файлов. Активный HTML/SVG не исполнять в origin панели |
| Временные ссылки | Общий список, файл, срок, создатель, отзыв и журнал обращений; пароль или лимит скачиваний — по потребности. Полные секретные URL не писать в журналы |
| Фоновые задания | Загрузки, backup, импорт, миграции и ремонт: единые статусы, прогресс, повтор, отмена, история ошибок |
| Импорт из S3 | Проверка подключения, предварительный расчёт, возобновляемое копирование с проверкой checksum и метаданных, отчёт о несовместимых свойствах |
| Wiki | Инструкции прямо из экрана, примеры клиентов, объяснение режимов хранения, действия при отказе диска, восстановление и проверка резервной копии |

Для автоматизации полезны события «объект создан/удалён» с webhook, подписью сообщения, фильтрами по префиксу и постоянной очередью повторов. Доставку проектировать как **как минимум однократную**: получатель должен обрабатывать дубликаты по идентификатору события. Не обещать «ровно один раз». Такой контракт используется и в уведомлениях Amazon S3. [S3 Event Notifications](https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html).

Генерацию превью, антивирусную проверку и другие тяжёлые обработчики лучше подключать отдельными необязательными worker-контейнерами. Основной сервис должен оставаться лёгким.

## 5. Как развить RAID-подобные режимы

Сохранить понятные пользователю названия и всегда пояснять: распределяются **целые объекты**, а не блоки одного файла.

Теоретический пример для четырёх независимых узлов по 2 ТБ, без служебных данных и запаса на восстановление:

| Режим текущей модели | Полезная ёмкость при равномерном размещении | Последствия отказа для данных |
| --- | --- | --- |
| RAID0: одна копия | До 8 ТБ | Потеря узла лишает единственных копий размещённых на нём объектов |
| RAID1: копия на всех четырёх узлах | До 2 ТБ | Данные остаются, пока есть хотя бы одна исправная копия; запись сейчас требует всех четырёх узлов |
| RAID10: две зеркальные пары | До 4 ТБ | Потеря обоих узлов одной пары лишает объектов этой пары; по одному отказу в каждой паре сохраняет копии |

Это оценка ёмкости и копий, **не гарантия доступности сервиса**: текущий координатор остаётся единственным. Фактическая ёмкость может быть меньше из-за распределения целых объектов, размеров дисков, метаданных и необходимого резерва.

Для развития полезны пулы хранения и политика «две/три копии» вместо обязательного зеркалирования на все узлы. Например, добавление сервера тогда сможет увеличивать ёмкость при неизменном числе копий. Политику задавать на бакет/пул с предварительным расчётом и безопасной миграцией. Текущий RAID1 при добавлении узлов увеличивает число копий, а не суммарную полезную ёмкость.

**Erasure coding** оставить отдельным будущим режимом: данные делятся на фрагменты данных и избыточности. Он экономит место по сравнению с полными копиями, но усложняет запись и ремонт. Число допустимых потерянных фрагментов нельзя приравнивать к числу любых серверов без учёта размещения. SeaweedFS, например, применяет EC к volumes, что влияет на объём восстановления. [Документация EC](https://github.com/seaweedfs/seaweedfs/wiki/Erasure-Coding-for-warm-storage).

## 6. Что действительно поможет скорости

Сначала измерить небольшие фотографии, крупные архивы, смешанное чтение/запись и несколько уровней параллелизма. Фиксировать пропускную способность, p95/p99, CPU, RSS, диск и сеть — с холодным и прогретым кэшем, во время ремонта и при медленном узле.

В текущем коде видны два кандидата для оптимизации: общий mutex записи/миграции и полная загрузка удалённой реплики во временный файл перед выдачей. Даже маленький Range может ждать целый объект. Следует исследовать более узкие блокировки и чтение проверяемыми фрагментами с checksum, сохраняя атомарность перезаписи и обнаружение повреждений.

Дополнительно полезны отдельные лимиты для пользовательских запросов и фонового ремонта, управление нагрузкой при переполнении очереди, ограничение памяти/временных файлов и наблюдаемые таймауты. RAM-кэш должен ускорять чтение; подтверждать долговечную запись только попаданием данных в RAM нельзя.

Обещать выигрыш в процентах или скорость относительно MinIO до воспроизводимых испытаний нельзя. Переход на другой язык, дедупликация и сжатие тоже должны опираться на профиль нагрузки.

## 7. Рекомендуемый порядок работ и критерии готовности

| Этап | Что делать | Как понять, что этап готов |
| --- | --- | --- |
| **Основа — начать сейчас** | Проект HA, форматов версий/multipart и постоянных задач; модель сбоев; исходные замеры; проверяемый backup | Документированное поведение при потере узла/связи, восстановление копии в отдельной установке, совместимый план изменения формата |
| **Повседневная работа** | Multipart, очередь в панели, приоритетные S3-операции, роли, квоты, метрики | Обрыв загрузки не требует повторять подтверждённые части; перезапуск не теряет состояние; проверенные SDK проходят CI; квоты выдерживают параллельные загрузки |
| **Защита данных** | Версии, lifecycle, автоматический backup и внешняя копия; Object Lock при backup-сценарии | Случайно удалённый файл восстановлен; копия проверена по содержимому; retention соблюдается всеми путями удаления |
| **Отказоустойчивый кластер** | Реализация выбранного HA, безопасный join/replace, возобновляемая миграция, независимые домены отказа | Проверены потеря лидера, разделение сети, заполнение диска, восстановление узла; без необходимого quorum новые записи не подтверждаются; подтверждённые данные сохраняются в пределах заявленной модели отказов |
| **Оптимизация по нагрузке** | Проверяемое чтение фрагментами, оптимизация блокировок, при необходимости EC/классы хранения | Повторяемый выигрыш на выбранной нагрузке без нарушения инвариантов и процедур восстановления |

Проектирование HA идёт с первого этапа. Если основная цель ближайшего развёртывания — непрерывная работа нескольких серверов, реализацию HA следует поднять раньше расширенного файлового менеджера и интеграций. Для личного локального хранилища раньше дадут пользу multipart и восстановление файлов.

В ближайший объём не стоит включать собственный CDN, биллинг облачного провайдера, SQL/AI-анализ содержимого, все варианты AWS IAM и одновременно S3/NFS/SMB. Они увеличивают сложность без подтверждённой пользы для исходной задачи.

**Предлагаемый первый практический пакет:** multipart с продолжением в панели, проверяемый backup/restore и диагностика; параллельно — проект отказоустойчивого каталога и формата версий. Это укрепит основу, на которой затем безопасно развивать остальные функции.
