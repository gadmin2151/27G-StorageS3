# Начальная настройка при первом запуске

**[English](INITIALIZATION.md) · Русский**

Параметры контейнера позволяют создать администратора, пользователей, S3-ключи и бакеты до начала обслуживания запросов. Это однократная инициализация нового экземпляра, а не способ менять существующую установку. Без параметров инициализации сохраняется обычный вход `admin` / `admin!123` с setup token.

## Самый простой способ: одна команда Docker

Для **новой установки на одном сервере** достаточно Docker Engine. Клонировать репозиторий, собирать образ, готовить JSON или запускать отдельный init-контейнер не нужно. Выполните:

```sh
docker run -d --name 27g-storage-s3 --restart unless-stopped --init \
  --read-only --cap-drop ALL --security-opt no-new-privileges:true \
  --tmpfs /tmp:size=64m,mode=1777 --stop-timeout 35 \
  -p 127.0.0.1:9000:9000 \
  --mount type=volume,src=27g-storage-s3-data,dst=/data \
  -e INIT_BUCKET=app-data \
  ghcr.io/gadmin2151/27g-storage-s3:0.3.4
```

Docker создаст постоянный том `27g-storage-s3-data`. Приложение проверит параметры запуска, создаст администратора `admin` со случайным паролем, приватный бакет `app-data` и пару S3-ключей с доступом к этому бакету, сохранит начальные реквизиты и запустит сервер. Всё выполняется в одном контейнере до приёма запросов.

Откройте [http://127.0.0.1:9000/console/](http://127.0.0.1:9000/console/), затем получите реквизиты на сервере:

```sh
docker exec 27g-storage-s3 cat /data/init-credentials.json
```

Войдите с полученным паролем администратора; setup token для этой настроенной учётной записи не нужен. **Access Key и Secret Key** предназначены для S3-приложения: endpoint `http://127.0.0.1:9000`, регион `us-east-1`, запросы path-style. Для другого имени бакета замените `app-data` в команде запуска. Если вашему пользователю требуется sudo, добавьте его перед командами Docker.

Файл реквизитов имеет права `0600`, секреты не выводятся в журнал контейнера. Сохраните их в менеджере паролей и не добавляйте файл в Git. После смены пароля или ключа в панели этот начальный файл не обновляется.

Перезапуск этого контейнера:

```sh
docker restart 27g-storage-s3
```

Инициализация отмечается на томе и выполняется один раз. Перезапуск не сбрасывает пароли, не создаёт ключи заново и не заменяет настройки бакета; объекты и базы SQLite не копируются. При обслуживании сохраняйте тот же том. Это ручное развёртывание; управляемое обновление через мастер установки применяется только к установкам, созданным самим мастером. Для уже работающей системы продолжайте её процедуру обновления, а не создавайте второй сервер этой командой.

Порт доступен только на loopback-адресе сервера. Для удалённого сервера откройте `ssh -L 9000:127.0.0.1:9000 user@server`, затем перейдите по адресу панели на своём компьютере. HTTPS и публичный адрес сервиса настраиваются отдельно при открытии доступа извне.

## Повторяемая инициализация бакетов через `27g`

Доступна в **0.3.4 / текущей сборке из исходников**. Образ содержит клиент `27g`: в стартовом скрипте можно создать несколько бакетов на уже работающем сервере:

```sh
27g create-bucket "my-bucket" --if-not-exists
27g create-bucket "my-bucket-2" --if-not-exists
27g create-bucket "my-bucket-3" --if-not-exists
```

Вариант `--if-no-exists` также поддерживается. Используйте два обычных ASCII-дефиса (`--`), а не длинное тире. Каждая команда принимает один бакет; флаг можно поставить перед именем или после него. Справка: `27g --help` и `27g create-bucket --help`. При запуске из исходников используйте `node src/cli.mjs create-bucket "my-bucket" --if-not-exists`.

Клиент отправляет подписанные S3-запросы работающему серверу и не открывает его том данных или SQLite. Отсутствующий бакет создаётся закрытым. С флагом ответ сервера `409 BucketAlreadyOwnedByYou` считается успехом; остальные ошибки, включая отказ в доступе или недоступность сервера, завершают команду с ошибкой. Объекты, политики и квоты существующего бакета не меняются. [Пример скрипта](examples/init-buckets.sh) использует `set -eu`: останавливается при первой ошибке, сохраняя уже созданные бакеты. Повторный запуск безопасно продолжает тот же список.

### Подготовить S3-ключ

В **Ключи доступа → Создать ключ** оставьте только операцию **Создание бакетов** (`createBucket`), включите **Все существующие и будущие бакеты**, а префиксы оставьте пустыми. Сохраните Access Key и Secret Key. Такой отдельный ключ может создавать бакеты с любыми допустимыми именами, но не может перечислять, читать, записывать или удалять объекты. После инициализации отзовите его, если повторные запуски больше не нужны.

Для новой установки с ограничением ключа ровно тремя именами задайте следующий `INIT_CONFIG_FILE` вместо простого `INIT_BUCKET`; подключение JSON описано ниже:

```json
{
  "version": 1,
  "users": [{ "username": "admin", "role": "admin" }],
  "keys": [{
    "label": "Bucket initialization",
    "owner": "admin",
    "buckets": ["my-bucket", "my-bucket-2", "my-bucket-3"],
    "permissions": ["createBucket"]
  }]
}
```

Сначала создаются учётная запись и случайный ключ, а бакеты создают последующие команды. Обычный ключ от `INIT_BUCKET=app-data` ограничен именем `app-data` и **не может создавать эти другие бакеты**. Для инициализации используйте отдельный ключ с нужными правами.

### Запустить в существующем Docker-контейнере

Нужен контейнер версии 0.3.4 или текущей сборки из исходников. В Bash-терминале введите отдельные S3-реквизиты, не записывая секрет в историю команд:

```bash
read -r -p 'Access Key: ' AWS_ACCESS_KEY_ID
read -r -s -p 'Secret Key: ' AWS_SECRET_ACCESS_KEY
printf '\n'
export AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
export S3_ENDPOINT=http://127.0.0.1:9000
export AWS_REGION=us-east-1
unset AWS_SESSION_TOKEN AWS_SECURITY_TOKEN

docker exec -i -e S3_ENDPOINT -e AWS_REGION \
  -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY \
  27g-storage-s3 sh <<'SH'
set -eu
27g create-bucket "my-bucket" --if-not-exists
27g create-bucket "my-bucket-2" --if-not-exists
27g create-bucket "my-bucket-3" --if-not-exists
SH
unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
```

Здесь endpoint — loopback **внутри работающего контейнера сервера**. Для сервиса `app`, управляемого Compose, замените `docker exec -i ... 27g-storage-s3` на `docker compose exec -T ... app`, сохранив флаги окружения и скрипт. Значения переменных доступны пользователю с правами просмотра Docker/процессов; для автоматического запуска предпочтительнее подключать файлы секретов.

### Запустить отдельным init-заданием Compose

Из корня исходников отредактируйте имена в `docs/examples/init-buckets.sh`. Создайте локальный файл секрета, не добавляя его в Git:

```bash
install -d -m 700 secrets
read -r -p 'Access Key: ' AWS_ACCESS_KEY_ID
read -r -s -p 'Secret Key: ' bucket_init_secret
printf '\n'
(umask 077; printf '%s' "$bucket_init_secret" > secrets/bucket-init-secret)
unset bucket_init_secret
export AWS_ACCESS_KEY_ID
export AWS_REGION=us-east-1
sudo chown 1000:1000 secrets/bucket-init-secret
sudo chmod 600 secrets/bucket-init-secret

docker compose -f compose.yaml -f compose.buckets-init.yaml up -d --build app
docker compose -f compose.yaml -f compose.buckets-init.yaml run --rm bucket-init
unset AWS_ACCESS_KEY_ID
```

Задание `bucket-init` ждёт готовности `app`, выполняет три команды по адресу `http://app:9000` и завершается. Скрипт подключается только для чтения, секрет передаётся файлом `/run/secrets/bucket_init_secret`; том данных хранилища заданию не подключается. Чтобы выбрать другой файл секрета на хосте, задайте `BUCKET_INIT_SECRET_FILE`. Файл должен читаться UID 1000 контейнера. Задание можно повторять с теми же реквизитами: учётные записи и настройки бакетов не сбрасываются. Эта конфигурация предназначена для одиночного Compose-развёртывания из исходников. В HA запускайте CLI через активный endpoint сервиса с подходящей сетью и подключёнными секретами.

### Параметры клиента

| Переменная | Назначение |
|---|---|
| `S3_ENDPOINT` | Адрес сервера, по умолчанию `http://127.0.0.1:9000`; без `/console`, `/api` и имени бакета |
| `AWS_ACCESS_KEY_ID` или `AWS_ACCESS_KEY_ID_FILE` | S3 Access Key либо читаемый файл с ним |
| `AWS_SECRET_ACCESS_KEY` или `AWS_SECRET_ACCESS_KEY_FILE` | S3 Secret Key либо читаемый файл с ним |
| `AWS_REGION` / `AWS_DEFAULT_REGION` | Регион подписи; приоритет у `AWS_REGION`, по умолчанию `us-east-1` |

Укажите значение либо его вариант `_FILE`, не оба сразу. Пути относятся к файловой системе процесса CLI; для отдельного контейнера подключите файлы. Последний перевод строки в файле реквизитов удаляется. Регион подписи должен совпадать с сервером. Клиент не принимает секреты в аргументах командной строки, временные AWS session tokens и флаг отключения проверки HTTPS-сертификата. Для внешнего endpoint настройте HTTPS и обычное доверие сертификату.

Код завершения: `0` — успех, `1` — ошибка сервера/сети, `2` — неверные аргументы или конфигурация. На запрос отводится 15 секунд. Перенаправления не выполняются: укажите конечный адрес сервиса в `S3_ENDPOINT`.

Параметры `INIT_*` и `--init-only` ниже отвечают за однократное **создание учётных записей и начальных настроек**. Команды `27g create-bucket` — отдельный, повторяемый шаг **после запуска сервера**, которому каждый раз нужен действующий S3-ключ.

## Из исходников: отдельный init-контейнер

Выполните из репозитория или распакованных исходников релиза на сервере с Docker Compose:

```sh
INIT_BUCKET=app-data docker compose -f compose.yaml -f compose.init.yaml up -d --build
docker compose exec -T app cat /data/init-credentials.json
```

Дополнительная конфигурация запускает одноразовый контейнер `init` с командой `node src/server.mjs --init-only`. Он использует тот же образ и том `coordinator`, что и `app`, не имеет доступа к сети и не открывает HTTP-порт. Приложение запускается только после успешной инициализации.

В примере создаются `admin` со случайным паролем, приватный бакет `app-data` и случайная пара S3-ключей с доступом к этому бакету. Вторая команда показывает созданные данные входа на сервере: файл имеет права `0600`, секреты не печатаются в журнал контейнера. Пароль администратора предназначен для панели `http://127.0.0.1:9000/console/`. Для S3-клиента нужны отдельные **Access Key и Secret Key**, endpoint `http://127.0.0.1:9000`, path-style и регион `us-east-1`. S3-секрет и setup token панели — разные данные.

Сохраните данные входа в менеджере паролей. В выходном файле находятся как сгенерированные, так и явно заданные начальные пароли и S3-секреты с отметкой способа создания. Файл `init-credentials.json` содержит секреты: не отправляйте его в Git или диагностику. После изменений в панели этот файл не становится актуальным справочником всех паролей и ключей.

Для последующих запусков и обновлений из исходников используйте обычный Compose, сохраняя прежние проект и том:

```sh
docker compose -f compose.yaml up -d --build
```

Конфигурация init предназначена для первого запуска. Не запускайте одноразовый процесс, пока `app` работает с тем же томом. При повторной попытке прерванной инициализации сначала остановите `app` и повторите исходную конфигурацию. Удалять том для повторной попытки не нужно.

У мастера установки собственный управляемый Compose и проверки обновления. Этот дополнительный способ запуска из исходников не меняет мастер и не добавляет ему новых параметров.

## Простые переменные окружения

Чтобы выполнить только инициализацию без запуска приложения, запустите сервис init отдельно:

```sh
INIT_BUCKET=app-data docker compose -f compose.yaml -f compose.init.yaml run --rm --build init
docker compose run --rm --no-deps app cat /data/init-credentials.json
docker compose -f compose.yaml up -d
```

При прямом запуске через Node.js флаг однократной инициализации сервера — `--init-only`:

```sh
INIT_ENABLED=true INIT_BUCKET=app-data DATA_DIR=./data node src/server.mjs --init-only
```

Без `--init-only` сервер после настройки начинает обслуживать запросы. Не запускайте второй процесс на каталоге данных уже работающего координатора.

Обычный сервер тоже сам читает эти параметры; отдельный init-контейнер необязателен. В своей конфигурации Compose передайте их непосредственно сервису `app`:

```yaml
services:
  app:
    environment:
      INIT_ENABLED: "true"
      INIT_ADMIN_USERNAME: admin
      INIT_BUCKET: app-data
```

Сохраните постоянный том `/data`. Сервер завершит инициализацию до приёма запросов приложения. Базовый `compose.yaml` из репозитория сам не передаёт переменные `INIT_*` хоста в контейнер; используйте такое сопоставление `environment` или готовую конфигурацию init.

`compose.init.yaml` передаёт эти переменные в `init`; обычный контейнер `app` не получает секреты инициализации. Пустое значение считается отсутствующим. Любой параметр включает инициализацию; одного `INIT_ENABLED=true` достаточно для создания администратора со случайным паролем.

| Переменная | Назначение |
|---|---|
| `INIT_ENABLED` | Явное включение; в дополнительной конфигурации init по умолчанию `true` |
| `INIT_ADMIN_USERNAME` | Логин первого администратора, по умолчанию `admin` |
| `INIT_ADMIN_PASSWORD` или `INIT_ADMIN_PASSWORD_FILE` | Пароль или путь к читаемому файлу внутри контейнера; без значения пароль генерируется |
| `INIT_BUCKET` | Имя начального бакета; также создаёт S3-ключ с доступом к этому бакету |
| `INIT_BUCKET_ACCESS` | `private` по умолчанию либо `public-read` |
| `INIT_BUCKET_READ_PREFIXES` | JSON-массив префиксов публичного чтения, например `["images/"]` |
| `INIT_BUCKET_QUOTA_BYTES` / `INIT_BUCKET_QUOTA_OBJECTS` | Необязательные квоты, неотрицательные целые числа |
| `INIT_S3_ACCESS_KEY` | Необязательный заданный Access Key |
| `INIT_S3_SECRET_KEY` или `INIT_S3_SECRET_KEY_FILE` | Заданный S3-секрет или путь к его файлу; без значения генерируется |
| `INIT_CONFIG_FILE` | JSON-файл внутри контейнера для нескольких пользователей, бакетов и ключей |

Публичное чтение только по префиксу:

```sh
INIT_BUCKET=public-media INIT_BUCKET_ACCESS=public-read \
INIT_BUCKET_READ_PREFIXES='["images/"]' \
docker compose -f compose.yaml -f compose.init.yaml up -d --build
```

Анонимный просмотр списка объектов остаётся запрещённым. `public-read` разрешает чтение по подходящему пути, а не получение списка всех файлов. Пустой список префиксов разрешает чтение по всему бакету. Такие ссылки не истекают; временные ссылки остаются отдельной функцией.

Для заданных паролей и S3-секретов лучше подключать файлы: значения обычных переменных видны при просмотре конфигурации Docker. Не задавайте одновременно значение и его вариант `_FILE`. Пути всегда относятся к файловой системе контейнера. Для нескольких ресурсов используйте JSON вместо простых переменных пользователей, бакета и ключа; не смешивайте эти форматы ввода.

## Несколько пользователей, ключей и бакетов через JSON

В [примере JSON](examples/init.example.json) нет паролей и S3-секретов. Он создаёт администратора, оператора, два бакета и ограниченный ключ приложения; отсутствующие секреты генерируются. Измените пример публичного чтения, если все бакеты должны быть приватными.

Подготовьте отдельный каталог для этой новой установки:

```sh
install -d -m 700 secrets secrets/initialization
cp docs/examples/init.example.json secrets/initialization/config.json
# Отредактируйте secrets/initialization/config.json перед продолжением.
cat > secrets/init.override.yaml <<'YAML'
services:
  init:
    environment:
      INIT_CONFIG_FILE: /run/secrets/config.json
    volumes:
      - type: bind
        source: ./secrets/initialization
        target: /run/secrets
        read_only: true
        bind:
          create_host_path: false
YAML
sudo chown 1000:1000 secrets/initialization secrets/initialization/config.json
sudo chmod 700 secrets/initialization
sudo chmod 600 secrets/initialization/config.json
docker compose -f compose.yaml -f compose.init.yaml -f secrets/init.override.yaml up -d --build
docker compose exec -T app cat /data/init-credentials.json
```

Добавьте `sudo` перед командами Docker, если этого требуют права вашей учётной записи. Compose разрешает относительный путь подключения от первого Compose-файла, поэтому команды выполняются в корне проекта. Каталог `secrets/` исключён из Git и контекста сборки Docker. Сам пример с генерацией всех секретов не содержит паролей, но файлы с заданными данными входа должны оставаться закрытыми.

Образ работает от UID/GID **1000:1000**. Этой учётной записи нужен доступ к каталогу и чтению подключённых файлов. Дополнительным файлам паролей и секретов задайте того же владельца и права `0600`. Контейнер не сможет прочитать подключённый файл `0600`, принадлежащий root; объявление Compose secret само по себе не меняет владельца файла на сервере.

В JSON используется `version: 1` и следующие списки:

| Список | Поля |
|---|---|
| `users` | `username`, `role` (`admin`, `operator`, `viewer`); необязательные `password` или `passwordFile`, `quotaBytes`, `quotaObjects`, `language` (`en`, `ru`) |
| `keys` | `label`, `owner`; необязательные `role` (`readwrite`, `readonly`), `buckets`, `prefixes`, `permissions`, `accessKey`, `secretKey` или `secretKeyFile` |
| `buckets` | `name`; необязательные `quotaBytes`, `quotaObjects`, `access: {"mode":"private"\|"public-read","readPrefixes":[]}` |

Размер JSON-файла ограничен 256 КиБ. В свой список пользователей включите администратора. Отсутствующий пароль или секрет ключа генерируется. Файловые поля содержат пути внутри контейнера, например `"passwordFile": "/run/secrets/admin-password"`; относительные пути в JSON отсчитываются от каталога конфигурационного файла. Завершающий перевод строки в файле секрета удаляется. Владелец ключа должен существовать в инициализируемой системе. Имена бакетов соответствуют действующим правилам S3; пароли, роли, квоты и разрешения проверяются правилами приложения.

Заданный пароль должен содержать от 12 символов и не более 1024 байт UTF-8. Для Access Key допустимы 3–128 латинских букв, цифр, точек, подчёркиваний и дефисов, начиная с буквы или цифры. Secret Key — 32–512 печатных ASCII-символов без пробелов. Можно задать любую половину пары S3 независимо; отсутствующая половина генерируется.

Разрешения ключей: `read`, `list`, `write`, `delete`, `createBucket`, `deleteBucket`. Для приложения выбирайте только необходимые бакеты, префиксы и операции. Роли панели действуют на всё хранилище: S3-ключ, ограниченный одним бакетом, не ограничивает веб-панель своего владельца-оператора этим бакетом.

## Существующие данные, повторные попытки и HA

Инициализация проверяет входные данные и сохраняет отметку завершения. Успешно настроенный экземпляр игнорирует последующие изменения параметров, включая ссылки на файлы секретов, которые больше недоступны приложению. Пароли не сбрасываются, отозванные ключи не создаются заново, политики не заменяются. Дальнейшее управление выполняется через панель или авторизованный API.

После прерывания первой инициализации продолжается записанная операция, а не создаётся новый набор секретов. При ошибке HTTP-сервер не начинает обслуживать запросы. Исправьте указанную проблему конфигурации или доступа к файлу и повторите запуск без удаления данных. Если удалить источник bind-подключения, пока Compose ещё ссылается на него, сам Docker может отказать в создании контейнера раньше приложения; после настройки используйте обычный Compose, как показано выше.

Механизм не копирует объекты или базы SQLite и не выполняет миграцию существующих данных. Контракт совместимого обновления остаётся прежним.

В HA инициализация относится к созданию **первого авторитетного снимка избранным master**. Slave загружает этот снимок и не создаёт независимый набор учётных записей. Существующие метаданные HA имеют приоритет над параметрами инициализации. Одноразовая конфигурация init и команда `--init-only` предназначены для одиночного сервера; используйте обычный согласованный запуск из [HA.md](HA.md), а не этот overlay на обоих координаторах.

Для `compose.ha.yaml` добавьте переменные инициализации в `environment` сервиса `master`, а файлы конфигурации и секретов подключите к нему с доступом на чтение для UID 1000. Сначала подготовьте общие секреты HA по соответствующему руководству. Файл начальных реквизитов сохраняется на томе первого master и не копируется на slave. Перед использованием созданных реквизитов проверьте, что в кластере есть активный master.
