# Диски, каталоги, SMB и NFS

Основной контейнер 27g-StoregeS3 не получает Docker socket или право монтировать файловые системы. Для подключения носителей из панели используется **отдельный необязательный дисковый агент** на выбранном Linux-сервере. Агент умеет подключать существующую файловую систему и обслуживать blobs через защищённый API. Форматирование, разметка, удаление файлов пользователя и автоматическое отключение устройств не выполняются.

## Установка агента

1. Сохраните случайный секрет длиной не менее 32 символов в `secrets/disk_token`, с правами `0600`. Этот же секрет понадобится при добавлении агента в панели. Не используйте пароль администратора или S3-ключ.
2. Выберите `DISK_DIRECTORY` — каталог хоста, внутри которого разрешено выделять каталоги хранения. Compose показывает его агенту как `/external`; в панели указывайте `/external` или вложенный путь.
3. Запустите агент с основным Compose:

   ```sh
   docker compose -f compose.yaml -f compose.disks.yaml up -d --build disk-agent
   ```

4. В панели зарегистрируйте доступный координатору адрес агента, например `http://disk-agent:9200`, и секрет. Порт агента по умолчанию не публикуется на хосте. Для отдельного сервера используйте защищённую сеть/VPN либо HTTPS-прокси с доверенным сертификатом.

Файл `compose.disks.yaml` можно запускать отдельно; в этом случае подключение координатора к его сети/адресу нужно организовать самостоятельно. Агент выполняется с root и `CAP_SYS_ADMIN`, доступом к `/dev` и отключённым профилем AppArmor контейнера: это доверенная служба управления дисками, её API не предназначен для открытого Интернета. Привилегии не распространяются на контейнер веб-панели.

Нужны Linux с `/proc/self/fd`, Docker с поддержкой bind propagation, ядро с поддержкой CIFS/NFS и выбранной локальной файловой системы. SMB используется с шифрованием SMB 3.1.1/3.0; сервер должен поддерживать соответствующий режим.

## Виды источников

| Источник | Ввод в панели | Поведение |
| --- | --- | --- |
| Каталог | `/external/storage-a` | Существующий каталог внутри разрешённого корня. Агент создаёт только собственный подкаталог `.27g-storeges3` |
| Блочное устройство | `/dev/disk/by-id/...-part1` | Существующая свободная ext4, XFS или Btrfs. Носитель с разделами или уже смонтированная файловая система отклоняется |
| SMB/CIFS | `//server/share`, пользователь, пароль, при необходимости домен | Агент монтирует ресурс внутри своего контейнера; SMB1/2 не используются |
| NFS | `server:/export/path` | Используется NFSv4 с hard mount; доступ к экспорту настраивается на NFS-сервере |

Подключение `/dev` по умолчанию выключено. Для его разрешения задайте `DISK_ALLOW_BLOCK_DEVICES=true`. Агент требует доступную таблицу монтирования **хоста**, указанную в `DISK_HOST_MOUNTINFO_FILE`; Compose подключает `/proc/1/mountinfo` хоста только для чтения. Это предотвращает повторное монтирование устройства, которое занято хостом, но не видно в mount namespace контейнера. При прямом запуске на хосте можно указать `/proc/self/mountinfo`.

Проверка занятости повторяется перед каждым новым mount, включая перезапуск и кнопку повторного подключения. Ошибка определения mount не считается свободной точкой: агент прекращает операцию.

Список устройств и проверка занятости не резервируют устройство против другого администратора хоста. Не подключайте и не переразмечайте тот же носитель одновременно сторонними инструментами. Общие сетевые ресурсы также следует выделять этому хранилищу отдельно. Список имён и путей относится к окружению агента, а не компьютеру, на котором открыт браузер.

## Сохранность и повторное подключение

- Параметры подключения сохраняются **до** активации, поэтому после остановки на промежуточном шаге агент может продолжить с тем же идентификатором тома.
- В `.27g-storeges3/volume.id` записывается владелец. Другой агент/том не присвоит уже занятое хранилище автоматически. Для переноса нужны его состояние и исходный идентификатор; удалять маркер для обхода проверки нельзя.
- SMB-реквизиты хранятся в зашифрованном `disks.json`. `master.key` хранится отдельно в том же защищённом каталоге состояния; это защита конфигурации от случайного раскрытия, а не от администратора хоста. Временный файл credentials имеет права `0600`, удаляется после mount; остатки после аварии очищаются при запуске.
- В backup агента входят `master.key`, `host.id`, `disks.json`; также нужны все данные подключённых томов. Без `master.key` агент не восстановит секреты и токены узлов.
- Агент удерживает открытые дескрипторы каталогов. Исчезновение mount или замена каталога не перенаправит текущую запись в нижележащий каталог хоста. Проверка доступности выполняется до запроса и перед подтверждением записи. При потере источника возвращается ошибка; требуется восстановить подключение и повторить запрос.
- Повторная активация занятого запросами тома отклоняется. Изменённая файловая система/подмена папки не принимается молча.
- По умолчанию `host.id` — постоянный случайный идентификатор агента. Если несколько агентов обслуживают один физический хост, задайте им одинаковый уникальный `DISK_HOST_ID`, чтобы панель могла распознавать общий источник ёмкости. Не задавайте один идентификатор разным физическим серверам.

Две папки на одном физическом диске не создают независимые копии. SMB/NFS добавляют зависимость от сети и удалённого сервера; hard NFS mount при недоступности сервера может долго блокировать операции ядра. Статус «подключено» не доказывает устойчивость накопителя к отключению питания или выполнение обещаний `fsync` внешним NAS.

## Что проверено

Автоматические тесты используют временные каталоги и имитацию команд монтирования: проверяют ограничения источников, права на credentials, шифрование конфигурации, восстановление состояния, контроль владельца, проверку токена до обращения к диску и потерю каталога посреди HTTP PUT. При подмене каталога запрос получает ошибку и в новом нижележащем каталоге не появляется blob.

**Реальное монтирование физических устройств, SMB/NFS и запуск образа агента в Docker на текущем окружении не выполнялись.** Их нужно проверить на выделенном тестовом сервере до использования важных данных. Проверка `docker compose config` подтверждает только синтаксис конфигурации.
