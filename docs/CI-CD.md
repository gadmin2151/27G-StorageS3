# Сборки и релизы в GitHub

Workflow [CI and release](../.github/workflows/ci.yml) проверяет изменения, собирает контейнеры и публикует релизы 27G-StorageS3. Запуски и их фактический результат доступны в [GitHub Actions](https://github.com/gadmin2151/27G-StorageS3/actions). Работающие пользовательские серверы автоматически не обновляются.

## Что запускается

| Событие | Проверки и сборка | Публикация |
|---|---|---|
| Pull request | Тесты, конфигурации, Docker-сборка и проверки контейнеров | Нет |
| Push в `master` | Те же обязательные проверки | Образы `edge` и `sha-<полный commit SHA>` |
| Push тега `vX.Y.Z` | Те же проверки, соответствие тега версии в `package.json` | Образы `X.Y.Z` и `latest`, GitHub Release с файлами установки |
| Ручной запуск из Actions | Проверки и сборка | Нет |

Публикация разрешена только из исходного репозитория `gadmin2151/27G-StorageS3` при push в доверенную ветку или тег. Pull request, включая fork, не получает разрешения публиковать пакеты и релизы. Actions закреплены полными SHA коммитов.

Образы:

```text
ghcr.io/gadmin2151/27g-storage-s3
ghcr.io/gadmin2151/27g-storage-s3-disk-agent
```

Первый образ содержит координатор, веб-панель и обычный узел хранения. Второй предназначен для отдельного дискового агента. Например, версия 0.3.1 координатора — `ghcr.io/gadmin2151/27g-storage-s3:0.3.1`.

## Проверки перед публикацией

Задание `validate` использует Node.js 22, выполняет `node --test tests/*.test.mjs`, проверяет синтаксис shell-скриптов и конфигурации Compose. Для HA скачивается etcd 3.6.5 с проверкой закреплённого SHA-256; тесты работают с настоящими процессами etcd. В релизной сборке проверяется также архив исходников.

Задание `containers` собирает основной образ и дисковый агент, запускает контейнеры на GitHub runner и проверяет работу и сохранение данных после перезапуска. Дополнительно установщик выполняет настоящую установку и обновление с локальными релизными файлами: проверяются неизменность volume, содержимого объектов, учётных данных и настроек, отказ несовместимого формата до остановки сервера и отсутствие клонирования volumes. В этой проверке подменяется только скачивание релизных файлов; Docker и установщик запускаются на runner. Это отдельная проверка исполнения контейнера: одного `docker compose config` для неё недостаточно. Испытания не подключают реальные SMB/NFS-серверы или физические диски.

Задание `publish` зависит от успешного завершения обоих заданий. Образы собираются для `linux/amd64` и `linux/arm64`; для второй архитектуры при сборке используется QEMU. Проверка работающего контейнера выполняется на `amd64`, поэтому нельзя считать её испытанием контейнеров на реальном ARM-сервере. Публикация сопровождается OCI-метаданными, provenance и SBOM. Затем отдельное задание `release`, зависящее от `publish`, создаёт GitHub Release для тега версии.

## Релизные файлы

Стабильный релиз содержит:

| Файл | Содержимое |
|---|---|
| `install.sh` | Диалоговый установщик одиночного сервера |
| `27g-storage-s3-vX.Y.Z.tar.gz` | Исходники из релизного коммита с одним корневым каталогом |
| `SHA256SUMS` | SHA-256 установщика и архива |

Архив не должен включать рабочие volumes, `.env`, SQLite, токены или журналы. Установщик проверяет скачанный архив по `SHA256SUMS` и использует конкретную версию. Список контрольных сумм опубликован в том же GitHub Release: он обнаруживает повреждение/несоответствие файлов, но не является независимой криптографической подписью владельца.

Последний стабильный установщик доступен по постоянному адресу:

```text
https://github.com/gadmin2151/27G-StorageS3/releases/latest/download/install.sh
```

Для воспроизводимой установки закрепляйте версию в URL и аргументе `--version`, как показано в [инструкции установки](INSTALLATION.md).

## Настройки GitHub

Для публикации workflow использует встроенный `GITHUB_TOKEN`: отдельный PAT или пароль сервера в Secrets не требуется. Заданию `publish` нужны `packages: write` и `contents: read`, а отдельному `release` — `contents: write`. Проверки используют чтение содержимого. Если политика организации запрещает эти разрешения, публикация завершится ошибкой до их разрешения владельцем.

После первой публикации проверьте видимость обоих пакетов в **GitHub → профиль gadmin2151 → Packages → пакет → Package settings**. Новые пакеты GHCR по умолчанию приватны; публичные пакеты можно скачивать без входа. Для установки без GitHub-аккаунта задайте видимость **Public**. Публичный репозиторий сам по себе не гарантирует публичность впервые созданного контейнерного пакета. [Документация GitHub Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

Если пакет уже существовал и был опубликован вне этого workflow, проверьте связь с репозиторием и доступ Actions на запись. Установщик может собрать основной образ из релизных исходников, если скачать готовый образ пока нельзя.

## Выпуск новой версии

1. Измените версию в `package.json`, обновите пользовательскую документацию и `docs/PROJECT_MEMORY.md`.
2. Отправьте проверенный коммит в `master` и дождитесь успешного workflow.
3. Создайте стабильный тег с той же версией и отправьте его в GitHub:

   ```sh
   git tag -a v0.3.1 -m "27G-StorageS3 0.3.1"
   git push origin v0.3.1
   ```

4. Дождитесь успешных `publish` и `release`, проверьте релизные файлы и доступность обоих образов без авторизации, если они предназначены для публичной установки.

В примере `v0.3.1` — конкретный выпуск; для следующего релиза используйте новую версию. Не переносите уже опубликованный тег на другой коммит и не заменяйте файлы релиза другой сборкой под прежним номером. Образ `edge` отслеживает разработку в `master`; `latest` предназначен для последнего стабильного выпуска. Для серверов предпочтительны конкретная версия или digest, как в установщике.
