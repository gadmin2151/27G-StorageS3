# Master/slave и кворум метаданных

HA использует **два полноценных координатора** — master и slave — и **три голосующих процесса etcd**. Один etcd располагается на хосте master, второй на хосте slave, третий на независимом хосте-арбитре. Арбитр хранит зашифрованные метаданные и участвует в кворуме; файлы пользователей через него не передаются. Два голоса из трёх нужны для выбора активного master и подтверждения изменений.

При недоступности кворума узел прекращает обслуживать запросы к данным и не подтверждает записи. Один только сетевой балансировщик или общий файл SQLite не заменяет кворум. Для одиночного сервера etcd не требуется: HA включается только при заданных `HA_ETCD_ENDPOINTS`.

## Что подтверждает запись

1. Активный координатор проверяет владельца lease линейным чтением etcd.
2. Приложение записывает неизменяемые blobs и все обязательные реплики. Части multipart также должны быть реплицированы до фиксации своих метаданных.
3. Временные изменения локальных SQLite не видны другим HTTP-запросам: HA guard упорядочивает запросы и обслуживание.
4. Координатор формирует единый снимок каталога, пользователей/ключей/политик, временных ссылок и multipart. Снимок сжимается и шифруется AES-256-GCM общим `master.key`.
5. Одна транзакция etcd одновременно проверяет владельца lease и предыдущую ревизию каталога, затем сохраняет новый снимок. Только после её успеха отправляется HTTP-ответ, подтверждающий изменение.

Если кворум потерян или появился другой master, транзакция не проходит. Старый координатор снимает с себя активную роль, восстанавливает последнюю подтверждённую локальную проекцию и остаётся недоступным до получения актуального состояния из etcd. Даже если старый процесс оживёт после длительной паузы, его прежний lease не позволит зафиксировать изменения.

Ответ может потеряться уже после успешного commit. Как и для других сетевых хранилищ, ошибка соединения не доказывает, что запись отсутствует: клиент должен проверить результат перед повтором. Имя/идентификатор запроса само по себе не обеспечивает дедупликацию повторов.

SQLite остаётся быстрой локальной проекцией. Это не репликация файлов SQLite: источником подтверждённого состояния служит транзакционно записанный снимок в кворуме etcd. После сбоя импорт может повториться. Локальный `ha-cluster.json` запрещает автоматически создавать новый пустой кластер из потенциально устаревшей SQLite, если прежние метаданные etcd исчезли.

## Запуск демонстрации

```sh
./scripts/init-ha.sh
docker compose -f compose.ha.yaml config --quiet
docker compose -f compose.ha.yaml up -d --build
docker compose -f compose.ha.yaml logs master
```

Панель и единый S3 endpoint: `http://127.0.0.1:9020`. Первоначальный токен входа берётся из журнала master. В «Кластере» выберите RAID1 и два HTTP-узла:

- `storage-master`, URL `http://storage-master:9100`;
- `storage-slave`, URL `http://storage-slave:9100`.

Токен узлов находится в локальном `secrets/node_token`. Не публикуйте его. Пока используются локальный узел координатора или топология без зеркалирования, запись файлов в HA отклоняется. Пустая начальная конфигурация допускается, чтобы открыть мастер настройки в панели.

Compose поднимает все процессы на **одном компьютере** и подходит для демонстрации отказов процессов. Он не защищает от потери этого компьютера или его общего диска. Для эксплуатации разместите master, slave и третий etcd на трёх независимых машинах; каждому процессу нужны свои данные/volume. Не монтируйте один каталог координатора в два контейнера.

`init-ha.sh` сохраняет существующие секреты. При подключении действующего хранилища необходимо согласованно перенести его `master.key` и setup token вместо генерации другого ключа. `ha-secrets.mjs` откажется заменять несовпадающий установленный ключ — иначе существующие зашифрованные S3-ключи и MFA-секреты стали бы нечитаемыми.

## Роли и маршрутизация

`HA_ROLE=master|slave` задаёт предпочтительную роль. Фактический master всегда определяется lease в etcd. Slave автоматически становится активным после освобождения/истечения lease прежнего master. Возвращение предпочтительного master не отбирает роль у работающего лидера. Изменённое предпочтение хранится в **локальном** `ha-node.json`, а не в общем снимке.

`GET /ha/ready` используется балансировщиком: HTTP 200 только у готового активного master, иначе 503. Caddy проверяет его каждые две секунды. `Caddyfile.ha` сохраняет исходный Host и не переписывает URI, что необходимо для подписей S3 SigV4. Недоверенный `X-27G-Client-IP` удаляется. Failover может сопровождаться короткими 503/502; клиенты должны повторять допустимые запросы с задержкой. Слепой повтор незавершённого multipart-complete/другого изменения требует проверки состояния.

Балансировщик в примере один. Для отказоустойчивого публичного адреса нужен отдельный доступный вход: внешняя балансировка либо два прокси с согласованным VIP/DNS. Это отдельный слой относительно выбора master. Его отказ не повреждает данные, но делает общий адрес недоступным.

## Сеть и секреты

В демонстрации etcd и хранилища доступны только внутри `internal` Docker-сети; порты 2379/2380/9100 наружу не опубликованы. На разных машинах используйте закрытую VPN/изолированную сеть и mTLS etcd для клиентских и межузловых соединений. Нельзя публиковать незащищённый etcd в Интернет: право записи в его keyspace означает управление кластером, даже если снимки зашифрованы.

Etcd поддерживает `--client-cert-auth`, `--trusted-ca-file`, `--cert-file`, `--key-file` и отдельные `--peer-client-cert-auth`, `--peer-trusted-ca-file`, `--peer-cert-file`, `--peer-key-file`. Координатор читает CA из `HA_ETCD_CA_FILE`, клиентский сертификат из `HA_ETCD_CERT_FILE`, ключ из `HA_ETCD_KEY_FILE`; для mTLS укажите все три пути и HTTPS-адреса в `HA_ETCD_ENDPOINTS`. Проверка сертификата не отключается. Секреты монтируются файлами только авторизованным процессам. Для внешнего S3/панели используйте HTTPS и один согласованный `PUBLIC_ORIGIN`.

Общий ключ шифрования задаётся файлом `HA_MASTER_KEY_FILE` (ровно 32 байта), общий начальный токен — `HA_SETUP_TOKEN_FILE`. Для каждого координатора задайте свой `HA_NODE_ID` и одинаковый `HA_CLUSTER_ID`. Полная потеря локального каталога означает повторное подключение с тем же ключом к существующему etcd, а не создание нового кластера.

## Текущие пределы

- На изменяющий запрос записывается полный сжатый снимок, а не changeset. Предел: **64 MiB JSON метаданных до сжатия**, по умолчанию **8 MiB зашифрованного сжатого снимка**. Данные файлов туда не входят. Превышение лимита отклоняет commit, снимает активную роль и восстанавливает подтверждённое состояние. У etcd в Compose `max-request-bytes=16 MiB`, учитывая Base64 JSON gateway.
- Полные снимки и общий guard ограничивают производительность большого каталога и параллельных длительных запросов. Это первая реализация HA; нагрузочное поведение не измерено. SQLite sessions/changesets доступны в Node, но сами по себе не обеспечивают атомарный commit трёх БД, fencing или восстановление после неуспешного кворума. Переход к журналу изменений и checkpoint требует отдельного протокола.
- **Физическая сборка мусора в HA отключена**, пока узлы хранения не проверяют fencing token при удалении. Иначе зависший старый master мог бы удалить файл, нужный новой подтверждённой версии каталога. Удаление через панель/S3 скрывает или удаляет метаданные, но место автоматически не освобождается. Неподтверждённые blobs также могут оставаться на узлах. Это существенное эксплуатационное ограничение.
- HA допускает только общие для обоих координаторов HTTP-узлы хранения с зеркальными копиями. `url: local` не годится: на разных машинах это разные диски. HTTP-узел на том же хосте допустим, если оба координатора обращаются к одному его сетевому адресу.
- Отказ **процесса координатора** допускает продолжение чтения и записи на другом координаторе при исправных узлах хранения. Отказ **всего хоста**, на котором расположен один из двух RAID1-узлов, сохраняет чтение оставшейся копии, но запись требует восстановления второй копии. Автоматическая запись в деградированное зеркало не включена.
- Сессии панели не реплицируются: после переключения нужно войти повторно. Пользователи, политики, MFA-состояние и S3-ключи сохраняются в подтверждённых метаданных.
- Вызовы любых изменений и фоновых процессов должны проходить через guard. Прямые записи в SQLite, обход guard или параллельный внешний процесс над локальной БД не поддерживаются.

## Резервное копирование и проверки

Сохраняйте согласованный снимок etcd (`etcdctl snapshot save` с проверкой восстановления), все storage volumes и общий `master.key`/setup/node-секреты. Один файл локального каталога координатора не заменяет backup etcd и blobs. Потеря двух голосующих volumes требует контролируемого восстановления etcd; нельзя удалять volumes и заново запускать пустой кворум над прежними координаторами.

Тесты `tests/ha.test.mjs` запускают настоящий кластер из трёх etcd и два независимых координатора с отдельными проекциями. `tests/ha-app.test.mjs` поднимает два отдельных процесса приложения и два HTTP-узла хранения, затем завершает master через SIGKILL. Бинарный файл задаётся явно:

```sh
ETCD_BINARY=/absolute/path/to/etcd node --test tests/ha.test.mjs tests/ha-app.test.mjs
```

Проверяются потеря master без штатного снятия lease, передача каталога/auth/shares/multipart новому master, разделение сети через HTTP-прокси, отклонение устаревшей записи после продвижения slave, потеря двух голосов, откат локальных неподтверждённых изменений и восстановление после возврата кворума. Отдельная проверка HTTP подтверждает, что неуспешный commit не выдаёт подготовленный Set-Cookie. Отказ одного HTTP-узла проверяет чтение оставшейся копии и отказ записи без полного зеркала. Без `ETCD_BINARY` интеграционные тесты явно пропускаются, а не подменяются имитацией Raft.

Официальные основы: [гарантии etcd](https://etcd.io/docs/v3.6/learning/api_guarantees/), [JSON gateway](https://etcd.io/docs/v3.6/dev-guide/api_grpc_gateway/), [SQLite API Node.js](https://nodejs.org/api/sqlite.html), [проверки upstream Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).
